# Agile Study Guide: Quick-Reference Memory Tables

## Module 4: Scrum Fundamentals

### 1. Scrum Roles
| Role | Primary Responsibility | Key Characteristics |
| :--- | :--- | :--- |
| **Product Owner (PO)** | Maximizes product value and manages the Product Backlog. | Represents the customer, prioritizes tasks based on business value. |
| **Scrum Master (SM)** | Ensures Scrum is understood and enacted. | Removes blockers/impediments, facilitates events, coaches the team. |
| **Development Team** | Delivers the potentially releasable Increment of "Done" product. | Self-organizing, cross-functional, estimates effort, executes the work. |

### 2. Scrum Events (Ceremonies)
| Event | Duration/Frequency | Primary Purpose | Key Output |
| :--- | :--- | :--- | :--- |
| **Sprint Planning** | Start of Sprint (e.g., 1-2 hrs) | Define what can be delivered and how to achieve it. | Sprint Goal & Sprint Backlog. |
| **Daily Scrum** | Daily (15 mins max) | Synchronize activities and identify blockers. | Daily plan, identified impediments. |
| **Sprint Review** | End of Sprint | Inspect the Increment and adapt the Product Backlog. | Feedback from stakeholders, updated backlog. |
| **Sprint Retrospective** | End of Sprint (After Review) | Inspect how the last Sprint went and identify improvements. | Actionable improvements for the next Sprint. |

## Module 5: User Stories & Estimation

### 3. The 3 Cs & User Story Format
| Concept | Description |
| :--- | :--- |
| **Card** | The physical/digital card holding the short stub and format: *"As an [Actor], I want [Action] so that [Value]."* |
| **Conversation** | The collaborative discussion between the team and PO to clarify details and identify gaps. |
| **Confirmation** | The Acceptance Criteria that must be met to confirm the story is successfully completed. |

### 4. The INVEST Criteria (For Good User Stories)
| Letter | Stands For | Meaning |
| :---: | :--- | :--- |
| **I** | **Independent** | Can be developed and prioritized without relying on other stories. |
| **N** | **Negotiable** | Flexible and open to discussion/refinement during development. |
| **V** | **Valuable** | Delivers clear value to the end-user or the business. |
| **E** | **Estimable** | Well-defined enough that the team can guess the effort required. |
| **S** | **Small** | Small enough to be completed within a single Sprint. |
| **T** | **Testable** | Has clear Acceptance Criteria to validate success. |

### 5. Acceptance Criteria vs. Definition of Done (DoD)
| Feature | Acceptance Criteria | Definition of Done (DoD) |
| :--- | :--- | :--- |
| **Scope** | Specific to a **single** User Story. | Universal; applies to **all** User Stories/Tasks. |
| **Focus** | Functional requirements and user expectations. | Technical quality, testing, and process standards. |
| **Example** | *"User can filter results by date."* | *"Code is peer-reviewed, tests pass, deployed."* |

### 6. Estimation Techniques
| Technique | Best Used For | Key Characteristics |
| :--- | :--- | :--- |
| **T-Shirt Sizing** | High-level backlog grooming. | Uses S, M, L, XL to quickly gauge rough effort. |
| **Modified Fibonacci** | Detailed Sprint Planning. | Uses 1, 2, 3, 5, 8, 13 to reflect non-linear complexity. |
| **Planning Poker** | Gaining team consensus. | Simultaneous voting; exposes hidden risks if votes vary widely. |
| **Spikes** | Handling high uncertainty. | Time-boxed research tasks to close knowledge gaps before sizing. |

## Module 6: Liftoffs & Team Alignment

### 7. Strategic Alignment: Purpose vs. Mission vs. Vision
| Term | Answers the Question... | Example |
| :--- | :--- | :--- |
| **Purpose** | *Why do we exist beyond making a profit?* | "To empower every person to achieve more." |
| **Mission** | *What is our current, actionable objective?* | "Increase driver onboarding by 20% in 3 months." |
| **Product Vision** | *What are we building and why does it matter?* | "To create a flexible scheduling system that reduces no-shows." |

### 8. Success Metrics Categories
| Category | What It Measures | Examples |
| :--- | :--- | :--- |
| **Technical** | System performance and code quality. | Bug count, Mean Time to Recovery (MTTR), Deployment frequency. |
| **Business** | Customer satisfaction and value generation. | Net Promoter Score (NPS), Retention rates, Conversion rates. |
| **Operational** | Team efficiency and workflow speed. | Velocity, Lead time for changes, DoD compliance percentage. |

### 9. The Team Charter (The "Team Contract")
| Component | What It Does | Example |
| :--- | :--- | :--- |
| **Definition of Done** | Sets the baseline quality standard. | "All code must pass automated security scans." |
| **Working Agreements** | Establishes rules for collaboration and behavior. | "Update Jira daily; cameras on during standup." |
| **Team Calendar** | Outlines recurring events and milestones. | "Sprint Planning is every other Monday at 10 AM." |
